# Offline emergency maintenance package

Scope: `shiftoryx-public-demo` and exactly `demo.shiftoryx.gr`, `demo-fuel.shiftoryx.gr`, `demo-cafe.shiftoryx.gr`, `demo-salon.shiftoryx.gr`, `demo-market.shiftoryx.gr`. This directory is an offline proposal. No live baseline has been captured; no containment has been deployed or proven. R1 remains BLOCKED. `CONTROLLED_DEPLOYMENT_QUALIFICATION_READY=NO`; `PUBLIC_DEMO_RELEASE_READY=NO`.

`index.html` and `style.css` are static, with no script, Firebase initialization, Auth, analytics, external fetch, customer data or redirect. The output frontend must be attached to all five exact demo aliases on the dedicated project in one reviewed operation. Never detach them to a wildcard or production deployment. `firestore.rules` and `storage.rules` are separate emergency deny-all client Rules, not replacements for normal reviewed Rules in the repository. They do not constrain Admin SDK calls in Cloud Functions or stop already running invocations.

Run `node scripts/test-demo-maintenance.mjs` and `node scripts/build-demo-maintenance.mjs` locally. The builder validates source identities, paths, pinned static HTML/CSS/Vercel bytes, deny-all Rules and locked bytes, then writes a deterministic package to an OS temporary directory outside Git. Its SHA-256 identifies the package bytes. It does not query or change cloud state. Only the output `web/` subdirectory is a future static frontend candidate; `controls/` contains Rules, runbook and baseline instructions and must stay private. The emitted `controls/target.json` is a reviewed assignment manifest, not a record of actual host assignments.

`live-baseline.empty.json` is deliberately `EMPTY_UNVERIFIED`; the strict schema and `validateRecoveryBaseline` define a later external evidence record. This R3 live recovery baseline captures project/number/database/region/bucket/runtime identity, six Auth domains, five aliases, Rules release IDs, actual six historical or nine target Function revisions/triggers/state, both schedules, four reset phases/leases and admission/retention controls, and exact Storage object names/generations/sizes/available metadata checksums. It is distinct from R2's externally supplied hash-sealed fixture qualification baseline (`qualificationSha`, `contextHash`, fixture counts and generation); neither substitutes for the other, and a hash is not a digital signature. Each alias must identify a preserved frontend artifact. Observations and independent verification must fit the declared capture window of at most one hour; old resource update times do not replace fresh observation times. A historical record that validates is not fresh deployment approval: recapture current evidence before a later rollout. Store any populated recovery baseline outside Git with only nonsecret digests and references. An evidence record marked `VERIFIED`, including the historical six-Function shape, is not restoration approval or proof that old broad Rules are safe. A missing or interrupted control state remains a stop condition.

Read `FUNCTION_CONTAINMENT.md` and `ROLLBACK.md` before any separately authorized cloud work. Broker/global-entry fences are now locally tested; no new revision/config has been deployed. Observation dossiers are planning metadata, never VERIFIED recovery or restore proof. The old live direct-SDK Rules and six-Function frontend are not an endorsed rollback target. No user, membership, ticket, credential, stale PDF authorization or old broad Rules may be restored. Generation only moves forward through a separately approved, verified reset contract.
